# 热点公众号文章（wechat-hot-article）

把一句主题输入变成「热点检索 → 语义复核 → 事实核查 → 交互选题 → 材料补充 → 文章设计确认 → Markdown + 公众号 HTML」的连续工作流。

本 Skill 只负责编排。筛选规则归 `web-content-fetcher`，正文与文风范式归 `zailushang-article`；不得绕过两者的质量门槛。

## 最简用法

```text
/wechat-hot-article OpenAI Codex
```

默认查找最近 7 天的高热内容，按点赞排序，并直接使用 Chrome `Default` Profile 的 X 登录态。检索后先通过交互让用户选题，不直接写成文章。

可选写法：

```text
/wechat-hot-article AI 编程工具 --mode news
/wechat-hot-article OpenAI Codex --sort replies
/wechat-hot-article OpenAI Codex --cookies-file ~/Downloads/cookies.txt
/wechat-hot-article OpenAI Codex --interaction text
```

如果缺少主题，只问一句“想围绕什么主题找热点并写公众号文章？”这是开放输入，不为了使用结构化工具而硬造主题候选。

## 输入解析

主题之外的参数均可省略：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--mode hot\|news` | `hot` | `hot`：Top 视图、最近 7 天、按点赞；`news`：Latest 视图、当天、按评论 |
| `--sort likes\|replies\|reposts\|views` | 按 mode | 本地互动排序，不改变 X 检索视图 |
| `--since YYYY-MM-DD` | 按 mode | 覆盖默认起始日期 |
| `--reader <读者>` | 选题时推荐 | 核心读者，不平均迎合多个群体 |
| `--viewpoint <观点>` | 选题时推荐 | 用户已明确观点时必须保留为文章主线 |
| `--interaction auto\|text` | `auto` | `auto`：优先结构化交互，受限时回退编号选项；`text`：始终使用文字交互 |
| `--web-session <浏览器>` | `chrome` | 默认使用已授权的 Chrome 会话；仅用户显式指定时切换 |
| `--browser-profile <Profile>` | `Default` | 默认只使用 `Default`，不自动尝试其他 Profile |
| `--cookies-file <路径>` | 无 | 显式提供时替代默认浏览器会话 |
| `--out <目录>` | 自动日期目录 | 本次工作流根目录 |

本 Skill 已获得用户持续授权：默认直接读取 Chrome `Default` Profile 中的 X 登录态，不再逐次确认。授权仅限该浏览器和 Profile；用户显式提供 `--cookies-file` 或其他会话参数时，以当次指令为准。不得输出 Cookie 值，不得自动扩大凭据读取范围。macOS 系统级钥匙串提示仍由系统控制，不得绕过。

不要在参数解析阶段要求用户一次性补齐观点、经历和素材。先检索，再用候选帮助用户做选择。

## 交互规则

### 工具与回退

- `--interaction auto` 且运行环境允许时，使用 `AskUserQuestion` 提供选项；用户指定 `--interaction text`，或当前模式、宿主环境明确禁止该工具时，改用等价的 Markdown 编号选项。不得强行调用被禁止的工具，也不得因回退而跳过人工确认。
- 必经决策使用前台交互并等待回答，不在后台发起选题或设计确认。每个交互只处理当前决策点；相关问题可合并到一次调用，最多 4 问。
- 推荐项放在首位并标注“推荐”，选项标签保持简短；不要自行添加“Other”选项，宿主工具会提供自定义输入入口。
- 先展示候选背景、事实边界或设计摘要，再发起选择。不要把长 URL、完整事实卡片或大段正文塞进选项。
- 文字回退使用同一组选项，例如“请回复 1、2、3；也可直接说明修改内容”。两种模式具有相同的流程与质量门槛。

### 提问与回答

- 只问尚未确认的信息。用户通过参数、选题附言或上一条回答已经提供的读者、观点、经历和材料，不重复询问。
- 选题、核心观点和文章设计属于必经确认；真实经历、额外截图和补充数据属于可选材料。可选材料缺失时允许使用 `[补充你的真实经历]` 或 `待确认`，不得虚构，也不得无故阻塞。
- 用户选择“现在补充”后，再用一条明确的开放问题收取原文、链接或文件路径，并等待回答。真实经历保留用户原文，不要求用户把经历改写成文章。
- 不在交互问题中索取 Cookie、令牌或其他凭据，不要求用户粘贴秘密文件内容。
- 用户关闭或跳过结构化问题不等于选择推荐项。必经决策保持未确认，并提示可回复编号；可选项按既定默认值或占位处理，不重复弹同一个问题。
- 每次回答后用一句话记录已确认状态，例如“已选：选题 2；读者：技术团队负责人；真实经历：待补充”，再进入下一阶段。

默认输出：

```text
work/wechat/<YYYYMMDD>-<slug>/
├── fetch/                 # web-content-fetcher 原始输出
├── input-pack.md          # 选定题后的写作输入包
└── article/
    ├── design.md          # 第一次文章设计确认
    ├── article.md         # 正文源文件
    └── article.html       # 公众号粘贴版
```

## 阶段 1：热点检索与筛选

1. 从主题提取规范主题、必要别名和 X 检索式。别名只覆盖实际产品或概念名称，不为扩大数量加入无关品牌词。
2. 按 `web-content-fetcher` 的公开用法调用其 `scripts/web_content.py`，使用 `--topic`、必要的 `--topic-alias`、`--query`、`--limit 50 --min-wechat-score 70 --out <根目录>/fetch`。默认同时传入 `--web-session chrome --browser-profile Default`；用户显式提供 Cookie 文件或其他会话参数时改用当次指定方式。
3. 未验证的检索式或会话先小批量测试，通过后再扩大到 50 条；已验证时可直接抓取 50 条。
4. 不得因需要读取默认浏览器凭据而暂停确认。默认会话失败时如实报告错误，不自动切换其他浏览器、Profile 或 Cookie 文件。
5. 检查 `manifest.json` 的错误和候选统计。没有候选时如实报告失败；有候选但全部淘汰时报告“没有合适内容”，不得使用 `rejected.jsonl` 凑数。
6. 阅读入选正文做语义复核，确认主题由正文前两句主导、新闻点或实用信息清楚；必要时复核淘汰清单纠正明显误判。
7. 互动排序只代表本次已抓取且通过筛选的候选，不称为 X 全量热榜。报告候选数、入选数、淘汰数和互动数据抓取时间。

没有合适内容时，可提供一次结构化后续选择：“扩大时间范围（推荐）”“切换 hot/news 模式”“修改主题或别名”“停止”。根据实际检索情况调整选项，不默认降低 70 分门槛，不自动反复重试；等待用户选择后再行动。

## 阶段 2：核查事实并交互选题

对最有写作价值的候选，用官方文档、公告或一手来源核实产品行为、版本、价格、日期、故障等易变事实。互动量和公众号适配分不代表真实性。

向用户展示最多 3 个实际可行的选题；不足 3 个时按实际数量展示。每个选题只包含：

- 推荐角度及核心读者；
- 可主张的核心观点；
- 主线热点、关键互动数据和原始 URL；
- 已核实事实及一手来源；
- 还缺少的真实经历或材料；
- 主要事实或版权风险。

优先推荐“热点作引子、实践或判断作主线”的角度，避免热帖摘要、引流话术和未经核实的收益宣传。

展示事实卡片后，发起“选择本次写作选题”交互：

- 每个选项对应一个选题，标签使用“选题 N：短标题”，描述概括核心读者与观点；推荐项放首位。
- 可增加“都不合适”，但不能用它替代实际候选。
- 用户选择某个选题，即确认采用其推荐读者和核心观点；用户附带的 `--reader`、`--viewpoint` 或自定义修改优先，不再重复确认。
- 用户选择“都不合适”时，询问希望调整的方向，保持未选题状态。

**在这里暂停。** 用户确认前不得生成 `input-pack.md`、`design.md` 或正文。

## 阶段 3：交互补充材料并生成写作输入包

选题确认后，先检查缺失项，再通过一次最多 4 问的结构化交互收集材料；没有缺失项时不额外打断。

1. **真实经历：**根据文章需要提供“现在补充（推荐）”“保留经历占位”“本文不涉及个人经历”。用户选择现在补充后，收取经历原文，至少引导说明场景、遇到的问题、尝试过的处理和结果；不得替用户编造细节。
2. **支持材料：**如现有证据不足，提供“补充链接或文件”“不补充”。收到路径或链接后先核验可用性与版权，不把所有材料都堆进正文。
3. **未决事实：**只针对无法自行核查且影响核心观点的事实，提供“补充一手来源”“标记为待确认”“放弃该主张”。能通过官方来源核实的内容先自行核查，不推给用户。
4. **读者或观点：**仅当用户选择修改，或设计时发现原推荐不成立，才再次询问；否则沿用选题确认结果。

将选定内容和交互结果写入 `<根目录>/input-pack.md`，至少包含：

```markdown
# 写作输入包

## 主题
## 核心读者
## 核心观点
## 交互确认
记录选题、读者与观点来源，以及用户已提供的修改；未回答的可选项不记为已确认。
## 热点主线
新闻点、原始 URL、互动数据及抓取时间、选题理由。
## 已核实事实
逐项记录事实和一手来源 URL；未经核实的内容明确标记，不写成事实。
## 支持材料
用于佐证的入选帖、对比观察、工具行为或数据。
## 真实经历
用户提供的经历原文；缺失时写明需要 `[补充你的真实经历]`，不得虚构。
## 事实边界与版权注意
## 输出要求
WeChat-ready HTML；article.md 与 article.html 写入 <根目录>/article/。
```

热点是背景与证据，用户的观点和真实材料是文章主线。只选 1 条主线热点，佐证通常不超过 4 条。

## 阶段 4：调用写作 Skill 并交互确认设计

调用 `Skill` 工具加载 `zailushang-article`，把 `input-pack.md` 的内容和输出路径作为写作输入，明确要求：

- 目的地为微信公众号，使用 `WeChat-ready HTML` 模式；
- 先完成并保存 `<根目录>/article/design.md`；
- 保留已确认的核心观点、事实边界和真实经历；
- 不生成或要求 `hero.png`，不切换到 `human-wechat-article` 的出版流程。

保存 `design.md` 后，向用户展示文件路径及读者、观点、开头场景、章节结构、缺失材料的简短摘要，再发起“是否确认文章设计”交互：

1. **确认并写正文（推荐）：**继续同一写作工作流。
2. **修改结构：**等待用户指出章节或论证顺序的修改，更新 `design.md`。
3. **修改观点：**等待用户给出新观点，同步检查 `input-pack.md` 与设计的一致性。
4. **补充材料：**等待用户补充原文、链接或文件路径，更新输入包和设计中受影响的部分。

修改后只重述变更摘要并再次确认，不重复已经完成的检索与事实核查。用户回复“确认”或选择“确认并写正文”后，继续生成完整 `article.md`，通过 Human-Feel Quality Gate，再生成 `article.html`。

**在 `design.md` 后再次暂停。** 不得把设计稿当成文章交付，也不得把用户关闭问题视为设计确认。

## 完成报告

最终只需向用户提供：

- `article.md` 和 `article.html` 的绝对路径；
- 选题、核心读者和核心观点的一句话摘要；
- 事实核查及公众号粘贴 readiness 结果；
- 仍需用户补充的经历占位及所在段落（如有）；
- 提醒人工预览并发布，本 Skill 不执行外部发布。

不要在最终回复中重复整篇正文，不要声称已经发布，也不要把中间检索或设计状态称为完成。不要为了多一次互动而强制增加交付后确认；用户需要修改或补充经历时，再在下一轮处理。

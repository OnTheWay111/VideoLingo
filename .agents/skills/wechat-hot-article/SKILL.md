# 热点公众号文章（wechat-hot-article）

把一句主题输入变成「热点检索与综合热度排序 → 语义复核 → 事实核查 → AI 自动选题 → 材料处理 → 自动文章与视觉设计 → Markdown + 封面/正文资产 + 公众号粘贴版 + 完整手机预览 + 人工式审核 → 提醒用户浏览确认」的连续工作流。

本 Skill 只负责编排。筛选与综合热度规则归 `web-content-fetcher`，正文与文风范式归 `zailushang-article`；不得绕过两者的质量门槛。视觉规则归本 Skill 的 `references/visual-design.md`，视觉制作不得改写正文或降低事实标准。新闻播报只是内容组织方式，仍须保留用户个人文风、事实边界、实践判断和可执行建议。

## 最简用法

```text
/wechat-hot-article OpenAI Codex
```

默认查找最近 7 天的内容，按综合热度排序，并直接使用 Chrome `Default` Profile 的 X 登录态。默认使用 `rich` 视觉模式和 `auto` 审核模式：AI 自动选题、生成文章与视觉设计，不再要求人工选题或确认正文与视觉设计，完成内容和格式审核后直接交付，并提醒用户浏览确认。需要恢复中途人工确认时，显式使用 `--review-mode confirm`。

可选写法：

```text
/wechat-hot-article AI 编程工具 --mode news
/wechat-hot-article OpenAI Codex --sort replies
/wechat-hot-article OpenAI Codex --article-style briefing
/wechat-hot-article OpenAI Codex --article-style briefing --missing-materials skip
/wechat-hot-article OpenAI Codex --visual-mode standard
/wechat-hot-article OpenAI Codex --review-mode confirm
/wechat-hot-article OpenAI Codex --interaction text
```

如果缺少主题，只问一句“想围绕什么主题找热点并写公众号文章？”这是开放输入，不为了使用结构化工具而硬造主题候选。

## 输入解析

主题之外的参数均可省略：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--mode hot\|news` | `hot` | `hot`：Top 视图、最近 7 天；`news`：Latest 视图、当天；两者默认按综合热度排序 |
| `--sort heat\|likes\|replies\|reposts\|views` | `heat` | 本地候选排序，不改变 X 检索视图；`heat` 综合时效、赞、评论、转发和浏览 |
| `--since YYYY-MM-DD` | 按 mode | 覆盖默认起始日期 |
| `--reader <读者>` | 自动判断 | 核心读者，不平均迎合多个群体；用户明确指定时必须保留 |
| `--viewpoint <观点>` | 自动判断 | 用户已明确观点时必须保留为文章主线 |
| `--article-style deep\|briefing` | `deep` | `deep`：单主线热点深度文章；`briefing`：2–3 条已核实事件组成新闻播报，与 `--mode news` 的检索视图含义不同 |
| `--missing-materials ask\|skip` | `ask` | `ask`：按缺失项询问可选材料；`skip`：跳过需要人工补充的可选材料，不等待、不占位、不虚构 |
| `--visual-mode rich\|standard\|text` | `rich` | `rich`：封面、视觉计划、配图决策、完整预览和人工式审核；`standard`：简洁排版、可选封面；`text`：用户明确选择纯文字时免封面 |
| `--review-mode auto\|confirm` | `auto` | `auto`：AI 自动选题和设计，生成后提醒用户浏览确认；`confirm`：恢复人工选题及正文与视觉设计确认 |
| `--interaction auto\|text` | `auto` | 仅 `confirm` 或可选材料交互使用；`auto`：优先结构化交互，受限时回退编号选项；`text`：始终使用文字交互 |
| `--out <目录>` | 自动日期目录 | 本次工作流根目录 |

用户用自然语言明确说“新闻播报”“资讯播报”时，按 `--article-style briefing` 处理；明确说“缺少材料直接跳过”“不等待人工补充”时，按 `--missing-materials skip` 处理；明确说“出版级视觉”“优化封面和排版”“人工审核内容和格式”时，按 `--visual-mode rich` 处理；明确说“AI 自动选题”“跳过正文与视觉设计确认”“直接生成文章”时，按 `--review-mode auto` 处理；明确要求中途人工确认时，按 `--review-mode confirm` 处理。用户在当前任务中的明确指令优先于默认值。

`--missing-materials skip` 只跳过真实经历、额外截图、补充数据等可选写作材料，不跳过主题、核心读者、核心观点、事实核查或 `rich` 视觉质量标准。影响核心主张且无法核实的事实必须删除该主张、标记为待确认或放弃相关选题，不能用“跳过材料”包装成事实。

X 登录态固定为本机 Chrome `Default` Profile。本 Skill 已获得用户持续授权，每次检索直接读取这一会话，不再逐次确认，也不提供 `--web-session`、`--browser-profile`、`--cookies-file` 或其他会话覆盖参数。调用 `web-content-fetcher` 时必须显式传入 `--web-session chrome --browser-profile Default`，不得使用 `off`、其他浏览器、其他 Profile、Cookie 文件或凭据文件替代。不得输出 Cookie 值，不得扩大凭据读取范围；macOS 系统级钥匙串提示仍由系统控制，不得绕过。只有用户后续明确修改这项固定策略时，才允许变更。

不要在参数解析阶段要求用户一次性补齐观点、经历和素材。先检索，再由 AI 评估候选并作出有证据的选择。

## 交互规则

### 自动决策与人工确认

- `--review-mode auto` 是默认模式。AI 根据综合热度、语义复核、事实可核实性、实践价值和视觉表达空间自动选择选题、核心读者、核心观点、文章结构及视觉方向，不发起选题或设计确认，不在这些节点暂停。
- 自动决策不等于降低质量门槛。必须在 `input-pack.md` 记录候选比较和选题理由，在 `design.md` 与 `visual-plan.md` 记录设计依据，并明确标记“AI 自动决策”，不得写成“用户已确认”。
- `--review-mode confirm` 才恢复人工选题、正文设计和视觉设计确认。只有该模式使用前台交互等待这些决策；用户关闭问题不视为确认。
- 可选材料仍由 `--missing-materials` 控制。`ask` 模式可以收集材料，`skip` 模式不等待人工补充；两种模式都不得虚构。
- 文章生成后必须完成人工式内容和格式审核，再提醒用户浏览 `article.preview.html`、`article.md` 和 `review.md` 并确认。用户浏览确认是交付后步骤，不得再前置为生成阻塞条件，也不得以 AI 审核代替用户最终判断。

### 工具与回退

- 仅在需要交互时，`--interaction auto` 且运行环境允许，使用 `AskUserQuestion`；用户指定 `--interaction text`，或宿主环境禁止该工具时，改用等价的 Markdown 编号选项。
- 每个交互只处理当前决策点；相关问题可合并到一次调用，最多 4 问。推荐项放在首位并标注“推荐”，不要自行添加“Other”选项。
- 先展示候选背景、事实边界或设计摘要，再发起选择；不要把长 URL、完整事实卡片或大段正文塞进选项。

### 材料处理

- 只问尚未确认的信息。用户已经提供的读者、观点、经历、材料、文章形式、视觉模式和材料处理策略，不重复询问。
- `--missing-materials ask` 时，可选材料缺失允许使用 `[补充你的真实经历]` 或 `待确认`，不得虚构，也不得无故阻塞。
- `--missing-materials skip` 时，不发起可选材料补充问题，不写 `[补充你的真实经历]` 占位；正文按“本文不涉及个人经历”处理，只使用已有材料和已核实事实。封面和信息图仍按视觉模式制作，但不伪造产品截图或作者证据。
- 用户选择“现在补充”后，再用一条明确的开放问题收取原文、链接或文件路径，并等待回答。真实经历保留用户原文，不要求用户把经历改写成文章。
- 不在交互问题中索取 Cookie、令牌或其他凭据，不要求用户粘贴秘密文件内容。
- 每次实际回答后记录确认状态；自动模式则记录“AI 自动选题／AI 自动设计”，不得伪造用户确认记录。

默认输出：

```text
work/wechat/<YYYYMMDD>-<slug>/
├── fetch/                    # web-content-fetcher 原始输出
├── input-pack.md             # 选定题后的写作输入包
└── article/
    ├── design.md             # 文章设计确认
    ├── visual-plan.md        # 视觉系统、封面和正文配图决策
    ├── article.md            # 唯一正文源文件
    ├── article.html          # 公众号 body-only 粘贴版
    ├── article.preview.html  # 完整手机审核页面
    ├── hero.png              # rich 模式的封面
    ├── assets/               # 正文 PNG/JPEG/WebP/GIF 与可编辑源文件
    └── review.md             # 人工式内容和格式审核
```

## 阶段 1：热点检索与筛选

1. 从主题提取规范主题、必要别名和 X 检索式。别名只覆盖实际产品或概念名称，不为扩大数量加入无关品牌词。
2. 按 `web-content-fetcher` 的公开用法调用其 `scripts/web_content.py`，使用 `--topic`、必要的 `--topic-alias`、`--query`、`--limit 50 --min-wechat-score 70 --out <根目录>/fetch`。未显式指定排序时传入 `--sort heat`，同时考虑发布时间、赞、评论、转发和浏览；用户指定单项排序时保留其选择。每次必须同时传入 `--web-session chrome --browser-profile Default`，固定使用本机 Chrome `Default` 的 X 登录态，不接受其他会话覆盖参数。
3. 未验证的检索式先小批量测试，通过后再扩大到 50 条；已验证时可直接抓取 50 条。不得因需要读取固定浏览器凭据而暂停确认。
4. Chrome `Default` 会话失败时，如实报告错误并提示用户先在本机 Chrome `Default` 登录 X，再重试当前检索。不得改用 `--web-session off`、内置浏览器的未登录页面、其他浏览器、其他 Profile、Cookie 文件或凭据文件，也不得把公开网页搜索伪装成 X 热度检索结果。
5. 检查 `manifest.json` 的错误、候选统计和 `heat` 配置。没有候选时如实报告失败；有候选但全部淘汰时报告“没有合适内容”，不得使用 `rejected.jsonl` 凑数。
6. 阅读入选正文做语义复核，确认主题由正文前两句主导、新闻点或实用信息清楚；必要时复核淘汰清单纠正明显误判。`heat_score` 高不能替代语义复核或让淘汰帖入选。
7. 综合热度只代表本次已抓取候选内的相对表现，不称为 X 全量热榜。报告候选数、入选数、淘汰数、互动数据抓取时间和热度参考日期。

没有合适内容时，可提供一次结构化后续选择：“扩大时间范围（推荐）”“切换 hot/news 模式”“修改主题或别名”“停止”。根据实际检索情况调整选项，不默认降低 70 分门槛，不自动反复重试；等待用户选择后再行动。

## 阶段 2：核查事实并自动选题

默认从 `items.jsonl` 中按 `heat_score` 从高到低评估最有写作价值的候选，而不是只取最新或单一点赞最高者。结合 `heat_breakdown` 判断热度主要来自讨论、传播、曝光还是时效；同一事件的重复帖合并为一个选题，优先用综合热度更高且信息更完整者作主线，其余作为佐证。

对候选用官方文档、公告或一手来源核实产品行为、版本、价格、日期、故障等易变事实。互动量、综合热度和公众号适配分都不代表真实性。

AI 最多形成 3 个实际可行的选题；不足 3 个时按实际数量评估。`deep` 模式每个方向对应一个单主线角度；`briefing` 模式可将 2–3 条相互独立、均已核实的事件组成一个播报组合，并给出贯穿组合的共同判断，不能只把高热帖拼成清单。每个方向必须评估：

- 推荐角度及核心读者；
- 可主张的核心观点；播报组合还需说明各条新闻之间的共同判断；
- 主线热点、发布日期、`heat_score`、赞、评论、转发、浏览和原始 URL；播报组合逐条列出；
- 已核实事实及一手来源；
- 还缺少的真实经历或材料；`--missing-materials skip` 时标为“按策略跳过”，不因此降低事实要求；
- 主要事实或版权风险。

优先选择“综合热度较高且有实践或判断价值”的角度，以热点作引子、实践或判断作主线，避免热帖摘要、引流话术和未经核实的收益宣传。热度高但缺乏写作价值或无法核实关键事实的候选不推荐。播报组合优先选择能够覆盖不同产品行为、但和同一核心读者有关的事件，不为凑满 3 条纳入弱相关或未经核实内容。

`--review-mode auto` 时，AI 直接选择证据最充分、读者价值最高且适合视觉表达的方向并继续生成 `input-pack.md`、`design.md` 和正文，不发起人工选题，不暂停。将候选比较和选择理由写入输入包，标记为“AI 自动选题”。

`--review-mode confirm` 时，才向用户展示事实卡片并发起“选择本次写作选题”交互；用户确认前不得生成输入包、设计或正文。用户附带的 `--reader`、`--viewpoint` 或自定义修改优先。

## 阶段 3：处理写作材料并生成写作输入包

选题确定后，先检查缺失项和材料处理策略。

`--missing-materials ask` 时，通过一次最多 4 问的结构化交互收集材料；没有缺失项时不额外打断：

1. **真实经历：**根据文章需要提供“现在补充（推荐）”“保留经历占位”“本文不涉及个人经历”。用户选择现在补充后，收取经历原文，至少引导说明场景、遇到的问题、尝试过的处理和结果；不得替用户编造细节。
2. **支持材料：**如现有证据不足，提供“补充链接或文件”“不补充”。收到路径或链接后先核验可用性与版权，不把所有材料都堆进正文。
3. **未决事实：**只针对无法自行核查且影响核心观点的事实，提供“补充一手来源”“标记为待确认”“放弃该主张”。能通过官方来源核实的内容先自行核查，不推给用户。
4. **读者或观点：**仅当用户选择修改，或设计时发现原推荐不成立，才再次询问；否则沿用已确定的选题。

`--missing-materials skip` 时，不发起上述可选材料交互，直接执行以下规则：

- 真实经历、截图、补充链接和额外数据缺失时直接略过，不等待用户，不设置经历占位。
- 不虚构试用、购买、排障、团队实践或第一手观察；需要个人经历才能成立的段落整体删除，而不是改写成虚构故事。
- 已有官方资料足够时，正文按“本文不涉及个人经历”写作；可明确说明“未实际试用，因此不评价实测效果”，但不把这句话重复成固定模板。
- 无法核实且影响核心观点的事实仍按未决事实规则处理，不得因 `skip` 而保留错误主张。

将选定内容、决策依据、文章形式和材料处理结果写入 `<根目录>/input-pack.md`，至少包含：

```markdown
# 写作输入包

## 主题
## 核心读者
## 核心观点
## 决策记录
记录 review-mode、候选比较、AI 自动选题理由或用户确认结果、文章形式、材料处理策略、读者与观点来源；自动决策不得记为用户确认。
## 热点主线
新闻点、原始 URL、发布日期、heat_score 与热度构成、赞评转览数据及抓取时间、热度参考日期、选题理由。
## 已核实事实
逐项记录事实和一手来源 URL；未经核实的内容明确标记，不写成事实。
## 支持材料
用于佐证的入选帖、对比观察、工具行为或数据。
## 真实经历
用户提供的经历原文；ask 模式缺失时写明需要 `[补充你的真实经历]`，skip 模式写明“本文不涉及个人经历，无占位”，不得虚构。
## 事实边界与版权注意
## 输出要求
记录 article-style、visual-mode、missing-materials 和 review-mode；article.md、article.html、article.preview.html、visual-plan.md、review.md 及所选视觉资产写入 <根目录>/article/。
```

`deep` 模式只选 1 条主线热点，佐证通常不超过 4 条；热点是背景与证据，用户的观点和真实材料是文章主线。`briefing` 模式将模板中的“热点主线”展开为 2–3 条“播报主线”，每条只选 1 个新闻事件，逐条记录相同的数据口径和事实边界，全部佐证帖通常不超过 4 条。播报应以共同观点和行动建议串起各条新闻，不写成热帖摘要合集。

## 阶段 4：调用写作 Skill 并生成文章与视觉设计

调用 `Skill` 工具加载 `zailushang-article`，把 `input-pack.md` 的内容和输出路径作为写作输入，同时阅读本 Skill 的 `references/visual-design.md`，明确要求：

- 目的地为微信公众号，使用 `WeChat-ready HTML` 模式；
- 先完成并保存 `<根目录>/article/design.md` 与 `<根目录>/article/visual-plan.md`；
- 保留已确定的文章形式、核心观点、事实边界、材料处理策略和真实经历；
- `briefing` 模式采用“具体阅读场景 → 新闻索引 → 2–3 条分条播报 → 共同判断 → 行动建议”的结构，每条回答“发生了什么、为什么值得关注、事实边界是什么”；
- `skip` 模式不生成经历占位，不要求用户补充已跳过的材料，也不虚构第一手体验；
- `visual-plan.md` 记录统一设计令牌、封面核心对象/场景/判断、真实素材与授权依据、两个构图方向、至少两个正文配图候选及净收益决策、粘贴版与预览版边界、手机审核计划；
- 不切换到 `human-wechat-article` 的完整出版流程，但复制其真实素材优先封面、正文配图净收益、预览分离、像素审核和分类修复能力。

`--review-mode auto` 时，两个设计文件保存后不暂停、不等待确认，直接生成完整 `article.md`，通过 Human-Feel Quality Gate 后进入视觉制作。设计中写明“AI 自动设计”，不得写成“用户已确认”。

`--review-mode confirm` 时，向用户展示两个文件路径及读者、观点、文章形式、开头场景、章节结构、视觉模式、封面方向、正文配图取舍和材料处理摘要，再发起“是否确认文章与视觉设计”交互：

1. **确认并写正文（推荐）：**继续同一写作与视觉工作流。
2. **修改结构：**更新 `design.md`，并同步检查视觉计划。
3. **修改观点：**同步检查 `input-pack.md`、文章设计与视觉设计的一致性。
4. **修改视觉：**只更新 `visual-plan.md` 及必要的文章结构映射。
5. **补充材料：**仅 `ask` 模式主动提供；`skip` 模式不主动展示此项。

修改后只重述变更摘要并再次确认，不重复已经完成的检索与事实核查。用户确认后才继续正文；用户关闭问题不视为设计确认。

## 阶段 5：视觉制作、预览与人工式审核

1. 按 `references/visual-design.md` 和已确定的 `visual-plan.md` 制作资产。`rich` 模式必须有真实素材优先、经过像素审核的 `hero.png`、信息流缩略图和至少两个安全裁切；没有合适真实素材时才使用具体对象导向的生成方案。
2. 正文配图只制作信息增量为正且有证据支持的候选。文件型配图直接以 `![有用 alt](assets/name.png)` 写入 `article.md`，不得伪造截图、数据或模型能力。零配图必须有逐候选拒绝理由。
3. 先生成 body-only `article.html`：首行为 `<meta charset="utf-8">`，其余为单个外层 `<section>`，第一个可见文本是 canonical 开头，不插入 H1、封面、平台摘要或互动占位。再生成完整 `article.preview.html`：包含 UTF-8、viewport、标题和完整正文，发布字段与封面放在阅读区之后。
4. 分别检查内容、Human-Feel、图片引用、粘贴兼容、预览完整性和手机阅读节奏，不能用 HTML 合法代替视觉判断。按 `references/visual-design.md` 的“读者视角的扫描与层级”检查首屏新闻索引、H2/H3 定位、核心引用和行动清单；列表化或标题化必须同步写回 `article.md`，不得只在 HTML 添加可见内容。浏览器可用时，实际查看 390×844 或相近手机视口的首屏、完整正文、正文图片和封面缩略图。
5. 将人工式审核写入 `review.md`，分别记录内容审核与格式审核的实际发现和结论，包括事实来源、时效边界、夸大风险、封面裁切、配图净收益、首屏、H2 扫描路径、段落密度、横向溢出、中文编码、行动清单和资料来源。
6. 正文、封面和机械格式修复分通道处理，各最多两轮。每轮后重新检查受影响项；视觉和格式修复不得改变已确定的观点、事实、论证顺序和语言习惯。
7. 审核完成后明确提醒用户浏览 `article.preview.html`、`article.md` 和 `review.md` 并确认内容、封面、配图和格式。不得把 AI 自动审核写成用户已经确认，也不得在用户确认前执行外部发布。

## 完成报告

最终只需向用户提供：

- 可点击的文件链接和对应绝对路径；`rich` 模式另附封面与视觉设计链接；
- AI 自动选题或用户确认的选题、核心读者和核心观点的一句话摘要；
- 事实核查、人工式内容审核、封面/正文配图、粘贴兼容和手机预览结果；明确列出仍需人工注意的问题；
- 仍需用户补充的经历占位及所在段落（如有）；`skip` 模式明确写“无待补材料或经历占位”；
- 明确提醒“请浏览并确认文章内容和视觉格式；确认后再发布”，本 Skill 不执行外部发布。

文件链接统一使用 Markdown 格式，首要入口命名为“微信公众号粘贴版文章”，直接指向本次实际生成且已验证存在的 `article.html`：
